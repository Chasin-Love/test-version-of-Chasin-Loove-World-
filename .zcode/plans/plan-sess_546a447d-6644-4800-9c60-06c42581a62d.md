# MY UNIVERSE — Desktop Upgrade: Tauri 2 Shell + Real C++ Core + Cinematic Black Hole

**Goal:** Turn the project into a native desktop app for Linux + Windows (desktop-first, web keeps working), with the C++ engine made genuinely real (physics/simulation), and a capability-gated cinematic raymarched black hole tier.

**Honest scope note baked into the plan:** the visuals are GLSL on the GPU (equally fast from webview or C++). C++ delivers: the N-body/Kepler/noise simulation core, real memory headroom, native filesystem, and unlocking the render-quality tiers the web couldn't risk. The Three.js renderer stays — upgraded, not discarded.

---

## Phase 0 — Toolchain & scaffolding
1. Verify/install on this machine: Rust (rustup), CMake + MSVC Build Tools, `@tauri-apps/cli` (npm devDep). Node already present.
2. Scaffold `src-tauri/`: `tauri.conf.json` (devUrl `http://localhost:3000`, frontendDist `../dist`, bundle targets NSIS/MSI + deb/AppImage, window "MY UNIVERSE" with min-size + icon), `Cargo.toml`, minimal `main.rs`/`lib.rs`, capabilities file (mic permission, FS scope under app-data + realities resources).
3. Scripts: `desktop:dev` (`tauri dev`), `desktop:build`. Web flow (`npm run dev`/`build`) unchanged and must keep passing.

## Phase 1 — Make the C++ core real (cosmos_engine v2)
1. Extend `src/native/cosmos_engine.{hpp,cpp}` with flat `extern "C"` exports only:
   - `cosmos_step_batch` — integrate N bodies one frame (RK4 + softened gravity, already exists) plus Kepler/vis-viva per body (ported from `physicsEngine.ts`), writing positions/velocities/telemetry into caller buffers.
   - `cosmos_orbit_position` — the per-frame Kepler position solver the renderer uses today.
   - `cosmos_fbm3` — the CPU noise (`cpuFbm`) used by planet-landing terrain, SIMD-friendly.
   - `cosmos_version` — for honest telemetry.
2. Build targets: existing CMake shared lib (.dll/.so for native) **plus** an Emscripten build producing `src/native/wasm/cosmos_engine.js/.wasm`, committed as artifacts so the web build needs no emsdk (rebuild script documented).
3. `cpp_bridge.ts` v2 — loader chain: **desktop** → Tauri `invoke` → Rust FFI → C ABI; **web** → WASM; **fallback** → existing pure-TS. Async API reports which backend is active.
4. `engine.updateBodies` consumes the bridge (batch step per frame); `physicsEngine.ts` stays as reference/TS fallback; PhysicsHUD data shape unchanged.
5. `CppNativeEngineCard` rewritten to show **real** state: active backend (Native/WASM/TS), real benchmark from that backend, version — no more fake "C++20 READY_TO_BUILD" metadata.

## Phase 2 — Desktop shell integration
1. **Persistence to real files:** Tauri commands `state_read/state_write` (atomic) in app-data dir (`%APPDATA%/MyUniverse` / `~/.local/share/MyUniverse`). `state.ts` adapter: Tauri FS on desktop, localStorage on web; one-time migration imports the existing `my-universe:v4` snapshot on first desktop boot.
2. **Payload store:** Tauri commands `payload_put/get/delete/list` under app-data/payloads. `indexedDB.ts` keeps its exact 8-function export surface (OPFS/IDB on web, files on desktop) so consumers don't change. Encryption stays WebCrypto AES-GCM (works in both webviews).
3. **Reality daemon → Tauri commands:** `reality_list/create_folder/rename/bin_*` in Rust, same logic + same sanitize/containment rules as `realityDaemon.ts`/`paths.ts` (ported), operating on the bundled realities dir. Frontend gets `apiAdapter`: `window.__TAURI__` → invoke, else `fetch('/api/...')`.
4. **Pyodide offline:** vendor pyodide v0.26.4 into app assets; executors use asset URL on desktop, CDN fallback on web.
5. **Mic + fonts:** webview media permission handler (WebView2/WebKitGTK); vendor Google Fonts locally for offline use.

## Phase 3 — Engine & black hole cinematic tier
1. **Capability probe** (GPU string via `WEBGL_debug_renderer_info`, WebGL2, float-blend ext) → auto quality tier + user override (Low/Medium/Cinematic) in the HUD. Cinematic tier: pixelRatio ≤ 2, higher particle counts, bigger bloom, desktop-only extras (star flare sprite, meteor/nebula density).
2. **`src/engine/blackholeRaymarch.ts`** — raymarched tier: Schwarzschild null-geodesic bending, volumetric accretion disk with Doppler beaming + gravitational redshift, lensed starfield. Strictly capability-gated, auto-fallback to the composite on any shader-compile failure (reuse the `eventide-shader-error` hook), user toggle. Composite remains the default for web and weak GPUs — the infallibility philosophy is preserved, not discarded.
3. Wire the tier into `createBlackHole` call path in `engine.ts` behind the probe.

- Web: `npm run typecheck` + `npm run build` green after every phase.
- Desktop: `cargo check`, `tauri dev` boots a window with the engine running; state migration from localStorage works; reality CRUD goes through native commands; benchmark card shows the native backend; black hole tier toggles and falls back cleanly when forced to fail.

## Risks
- WebView2 also translates GL via ANGLE→D3D — hence the raymarch tier is probe-gated with automatic fallback (composite default).
- WebKitGTK variance on Linux — CI artifacts + fallbacks cover it; Electron remains an escape hatch if Linux webview proves weak.
- emsdk may not exist locally — WASM ships as prebuilt committed artifacts.

## Deferred
Full C++ Qt/Vulkan rewrite (Option C) stays a documented future path; storage schema versioning/vault refactor from Wave 2 of the earlier roadmap unchanged.
